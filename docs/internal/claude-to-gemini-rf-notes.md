Дата: 2025-02-20

## 2. Security — сравнение

### Что Gemini нашёл правильно:
- **DEBUG=True по умолчанию** — совпадает с моим анализом (п. 2.3)
- **SECRET_KEY = "change-me"** — совпадает (п. 2.2)
- **Нет SQLi** — совпадает (п. 2.7)

### Что Gemini пропустил (критическое):
- **Отсутствие аутентификации на dashboard и API** — это **самая серьёзная проблема безопасности** проекта (P0). Все endpoints открыты без login. Gemini это полностью упустил. Это удивительное упущение: просмотр `dashboard/views.py` и `orders/api_views.py` сразу показывает отсутствие `@login_required` и `IsAuthenticated`.
- **Отсутствие проверки принадлежности заказа в Telegram callbacks** — пользователь может подтвердить/отменить чужой заказ.
- **Парсинг callback_data без try/except** — `int(callback.data.split(":")[-1])` может упасть на некорректных данных.
- **Нет rate limiting** — возможность генерации тысяч заказов с расходом LLM-токенов.

### Спорные рекомендации Gemini:
- "Заблокировать использование дефолтных кредов для интеграций в PROD окружении" — идея правильная, но непрактичная без чёткого механизма определения PROD vs DEV. В проекте нет переменной `ENVIRONMENT`.
- "Фильтрация чувствительных данных при логировании" — валидное замечание, но второстепенное. Логирование `_post_with_retry` не dump'ит тела запросов с токенами.

**Вердикт по Security: Gemini нашёл 2 из 6 значимых проблем. Пропуск отсутствия auth — серьёзный недостаток анализа.**

## 3. Архитектура (SOLID) — сравнение

### Что Gemini нашёл правильно:
- **SRP нарушение в `dashboard/views.py`** — views вызывают Bpium, ApiShip, Telegram напрямую. Совпадает с моим анализом (п. 3.5), хотя я отнёс это к нарушению Dependency Inversion, а не SRP — обе интерпретации допустимы.
- **God Module `ai_parser/client.py` (~1000 строк)** — полное совпадение (п. 3.2).
- **Рекомендация выделить cleaners/mappers** — совпадает с моей рекомендацией `ai_parser/normalizers.py`.

### Что Gemini пропустил:
- **`ai_parser/services.py` (661 строк) — тоже God Module**. Функция `process_intake_message` выполняет 12+ ответственностей. Gemini не упомянул этот файл вообще.
- **Дублирование утилит `_env_bool/_env_int/_env_float`** в 4 файлах — конкретная, легко исправимая проблема DRY.
- **Нарушение DI**: `ai_parser/services.py` импортирует интеграции (Bpium, ApiShip, delivery). AI-парсер не должен знать о доставке и CRM.

### Спорные рекомендации Gemini:
- **"Django Signals `post_save` для OrderStatusHistory"** — это **антипаттерн** для бизнес-логики. Signals делают поток управления неявным и затрудняют отладку. Лучше инкапсулировать side-effects в Service Layer (как я рекомендую), а не прятать их в signal handlers. Django core team и большинство экспертов (Two Scoops of Django) рекомендуют избегать signals для бизнес-логики.
- **"Dependency Injection: прокидывать HTTP-сессию извне"** — корректная рекомендация, но низкоприоритетная. Тесты уже mock'ают клиентов через patch.

**Вердикт по Architecture: Gemini нашёл 2 из 5 проблем. Рекомендация Signals — спорная.**

## 4. Баги и тесты — сравнение

### Что Gemini нашёл правильно:
- **Низкое покрытие dashboard (57%) и integrations** — совпадает.
- **Catch-all `except Exception` может замаскировать баги** — валидное замечание.
- **Необходимость тестов на `storefront_view` и `order_status_update_view`** — совпадает (мой п. 5.2).

### Что Gemini пропустил:
- **Dead code** в `get_default_llm_client()` (строки 448-449) — конкретный баг, легко находимый при чтении кода.
- **`ACTIVE_ORDER_CONTEXT` в памяти бота** — теряется при перезапуске.
- **Race condition при параллельных update** — `order.save()` без `update_fields` и без `select_for_update()`.
- **`order.save()` и `customer.save()` без `update_fields`** — конкретные баги производительности и корректности.
- **Отсутствие тестов для `bot/handlers.py`** — 0 тестов для ключевого модуля.
- **Отсутствие тестов для API endpoints** — ни одного теста на `/api/orders/`.

### Спорные рекомендации Gemini:
- "Кастомные Exception классы вместо generic Exception" — правильно по духу, но `ApiShipError` и `YooKassaError` уже определены в проекте. Gemini не заметил, что кастомные исключения уже есть.

**Вердикт по Bugs/Tests: Gemini нашёл 2 из 8 проблем. Не выявил ни одного конкретного бага в коде.**

## 5. Python / ML Best Practices — сравнение

### Что Gemini нашёл правильно:
- **Отсутствие structured logging** — совпадает (мой п. 6.6).
- **Pydantic + Instructor — хороший выбор** — совпадает.

### Что Gemini пропустил:
- **`time.sleep()` в retry блокирует Django thread** — значимая проблема для production.
- **Отсутствие логирования latency LLM-вызовов** — важно для мониторинга.
- **`runserver` в production Dockerfile** — критичная DevOps-проблема.
- **Volume mount в docker-compose для production** — перезаписывает контейнер.

### Спорные рекомендации Gemini:

- **"Вынести промпты в YAML/JSON или Django БД"** — **спорно**. Промпты в проекте уже вынесены в отдельный модуль `ai_parser/prompts.py` (3 промпта, 31 строка). Это чистый, простой подход. YAML/JSON/DB — оверинжиниринг для 3 промптов. LangChain-style шаблоны добавляют зависимость без реальной пользы для MVP. Jinja2 для промптов — это антипаттерн: промпты лучше хранить в коде рядом с логикой, которая их использует.

- **"Вместо сложных эвристик ручного парсинга, лучше сразу кидать Validation Error и использовать retry через Instructor (Re-prompting)"** — это **фундаментально неверная рекомендация** для данного проекта. Вот почему:
  1. **Instructor retry работает только с OpenAI-совместимыми API.** GigaChat и YandexGPT используют собственные HTTP API без `instructor`. Re-prompting через Instructor для них невозможен.
  2. **GigaChat function calling нестабильно возвращает JSON.** Tolerant parsing (`_coerce_items`, `_normalize_order_extract_payload`) — это **необходимый** production-grade слой для работы с реальными RU-моделями. Без него pipeline будет падать на каждом третьем запросе.
  3. **Re-prompting удваивает latency и стоимость.** Для пользователя в Telegram ждать 20 секунд (2 × 10 секунд) вместо 10 — неприемлемо.
  4. **Проект уже демонстрирует 100% accuracy на 50 кейсах** с текущим подходом. Зачем ломать работающее решение?

  Gemini описал tolerant parsing как "хрупкий" (brittle), но на практике это **самая надёжная** часть AI-контура — именно она обеспечивает 100% accuracy. Рекомендация "убрать эвристики и положиться на retry" показывает непонимание реальных ограничений RU LLM-провайдеров.

**Вердикт по Python/ML: 1 полезная рекомендация (structured logging), 1 спорная (промпты в YAML), 1 вредная (убрать tolerant parsing).**

## 7. Заключение

**Gemini провёл поверхностный, но в целом корректный обзор верхнего уровня.** Он верно определил основные направления для улучшения (DEBUG default, SECRET_KEY, God Module client.py, coverage gaps), но:

1. **Пропустил критическую проблему безопасности** — отсутствие аутентификации на всех endpoints
2. **Не нашёл ни одного конкретного бага** в коде (dead code, race conditions, missing update_fields)
3. **Дал 1 потенциально вредную рекомендацию** — убрать tolerant parsing в пользу re-prompting (не работает с GigaChat/YandexGPT)
4. **Дал 1 спорную архитектурную рекомендацию** — Django Signals для бизнес-логики (антипаттерн)
5. **Не привёл ни одного примера кода** для исправлений

Отчёт Gemini подходит как **первичный скрининг** для менеджера, но **недостаточен как руководство к действию** для разработчика. Для реального рефакторинга нужен более глубокий анализ с привязкой к конкретным строкам кода и проверяемыми fix'ами.

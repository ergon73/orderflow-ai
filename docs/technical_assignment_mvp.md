# Техническое задание (Reverse Engineering) — OrderFlow AI MVP v2.1

## 1. Основание документа

Документ подготовлен на основе:
- исходного файла задания: `основной проект - текст задания.txt`;
- фактически реализованной системы (код, тесты, артефакты);

Дополнительное методическое основание (по ответам куратора в чате потока):

- границы MVP студент определяет самостоятельно;

Из этого следует формат текущего документа:
- это уточненное ТЗ по принципу reverse engineering (от реализованного решения к финальной формализации требований).

## 2. Цель проекта

Создать омниканальную AI-систему обработки заказов для e-commerce, которая:
- принимает заказы из Telegram, web-формы и email;
- извлекает структуру заказа из естественного языка;
- управляет статусами заказа через формализованную state machine;
- синхронизирует заказ с CRM;
- поддерживает оплату, доставку и менеджерский dashboard.

## 3. Границы MVP

### 3.1 Входит в MVP (in-scope)

- 3 канала intake: Telegram, web, email.
- AI parsing с пост-валидацией и slot filling.
- CRM синхронизация в Bpium.
- Оплата через YooKassa sandbox + fallback.
- Доставка через ApiShip (test contour) + fallback тарифы.
- Dashboard менеджера: список, карточка, статусы, аналитика, CSV, invoice.
- Базовая API документация (`/api/docs/`).
- Тесты и демо-артефакты (скриншоты, видео, датасет и отчеты).

### 3.2 Не входит в MVP (out-of-scope)

- Полный production hardening (TLS termination с боевым сертификатом, Vault, full observability stack).
- Формальные SLA-контракты с боевыми вендорами.
- Полноценная enterprise-поддержка L1/L2/L3 в эксплуатации.
- Финальная промышленная приемка по пентесту.

Эти пункты вынесены в post-MVP roadmap:
- `docs/production_readiness_roadmap.md`
- `docs/ux_cx_roadmap.md`

## 4. Функциональные требования

## 4.1 Этап 1: Проектирование

- `FR-01` Система должна иметь прозрачный data flow: Intake -> Parsing -> Order -> Integrations.
- `FR-02` Система должна хранить сущности `Customer`, `IntakeMessage`, `ExtractionAttempt`, `Order`, `OrderItem`, `OrderStatusHistory`.
- `FR-03` Должны быть доступны API endpoints для чтения заказа и смены статуса (с авторизацией).

Критерии приемки:
- модели и миграции применяются корректно;
- state machine валидирует переходы;
- API отражен в Swagger.

## 4.2 Этап 2: Прием заказов

- `FR-04` Telegram bot принимает текстовые заказы и callbacks (`Подтвердить`, `Исправить`, `Отменить`).
- `FR-05` Web storefront принимает заказ через форму.
- `FR-06` Email ingestion обрабатывает входящую почту через IMAP.
- `FR-07` Для каждого канала должен соблюдаться idempotency ключ.
- `FR-08` Единый pipeline обработки должен работать для всех каналов через `IntakeMessage`.

Критерии приемки:
- intake по каждому каналу создает `IntakeMessage` и `Order`;
- повторные события не создают дублей.

## 4.3 Этап 3: AI parsing

- `FR-09` AI parser извлекает позиции, контакты, адрес и служебные поля (`confidence`, `missing_fields`).
- `FR-10` Пост-валидация нормализует поля (телефон, обязательные слоты, канонические missing fields).
- `FR-11` При неполных данных заказ переводится в `needs_info`; при уточнении обновляется тот же `order_id`.
- `FR-12` Поддерживается мульти-провайдерный LLM контур (openai/vllm/yandexgpt/gigachat/mock) без изменения бизнес-логики.

Критерии приемки:
- стабильный parse на тестовом наборе;
- slot filling без смешивания контекста заказов.

## 4.4 Этап 4: CRM integration

- `FR-13` Реализована интеграция с CRM (в MVP выбран Bpium как эквивалент Google Sheets/Airtable).
- `FR-14` Реализован upsert записи заказа по `external_id=order_id`.
- `FR-15` Ошибки CRM не должны ломать основной pipeline (graceful degradation).

Критерии приемки:
- при `confirmed` запись в CRM создается/обновляется;
- при ошибке CRM заказ остается операбельным.

## 4.5 Этап 5: Доставка и оплата

- `FR-16` Реализована интеграция службы доставки через ApiShip (test contour).
- `FR-17` Реализован расчет доставки через ApiShip calculator с fallback на локальные тарифы.
- `FR-18` Реализована платежная логика через YooKassa sandbox (create/check payment) и manual fallback.
- `FR-19` Реализована генерация счета (PDF/HTML fallback).
- `FR-20` В заказе сохраняются поля доставки:
`shipping_provider`, `shipping_external_id`, `track_number`, `tracking_url`, `shipping_status_raw`, `shipping_synced_at`.

Критерии приемки:
- стоимость доставки рассчитывается (или fallback применяется без падения);
- тестовая отправка создается, трек-данные сохраняются;
- платежный статус синхронизируется;
- счет формируется и скачивается.

## 4.6 Этап 6: Dashboard менеджера

- `FR-21` Доступен список заказов с фильтрами и поиском.
- `FR-22` Доступна карточка заказа с историей и сменой статуса.
- `FR-23` Доступна аналитика (графики), CSV export, invoice.
- `FR-24` Доступ к manager endpoints защищен авторизацией.

Критерии приемки:
- UI позволяет сопровождать заказ end-to-end;
- невалидные переходы блокируются;
- каждое изменение статуса логируется в истории.

## 4.7 Этап 7: Тестирование

- `FR-25` Должны быть автотесты на ключевую бизнес-логику и интеграционные контуры (с моками).
- `FR-26` Должны быть подготовлены артефакты сдачи:
GitHub, скриншоты, демо-видео, API docs, демо-магазин.

Критерии приемки:
- тест-ран проходит без регрессий;
- демонстрационные сценарии A/B/C/D воспроизводимы.

## 5. Нефункциональные требования (уровень MVP)

- `NFR-01` Базовая безопасность: auth на dashboard/API, защита callback ownership, безопасные defaults в runtime settings.
- `NFR-02` Базовая надежность: health endpoint, контейнерные healthchecks, fallback при сбоях внешних сервисов.
- `NFR-03` Наблюдаемость уровня MVP: application logs + masking secrets + ключевые runtime события.
- `NFR-04` Документируемость: архитектура, ограничения, privacy-note, roadmap в `README`.
- `NFR-05` Технический baseline после post-audit hardening:
web-контур в Docker запускается через `gunicorn`, внешние side effects в AI pipeline выполняются после commit транзакции.

## 6. Ограничения и допущения

- Система сдана как расширенный MVP, не как production-ready контур.
- Внешние интеграции используются в sandbox/test-профилях, где применимо.
- Для эксплуатации в production обязателен этап production readiness по отдельному плану.
